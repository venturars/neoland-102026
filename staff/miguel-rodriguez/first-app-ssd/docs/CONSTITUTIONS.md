# Constitution — first-app-ssd

Status: **foundation approved by Miguel on 2026-10-19; initialization and all agreed contact operations implemented and verified under specifications 001–006**.

## Purpose

A local contact-management application for learning SDD. It creates, updates,
deletes, lists, and finds users by email. A user is a contact record, not a login
account. Authentication, passwords, HTTP APIs, notebook setup, and graphical
interfaces are outside the initial scope.

The business logic will be reusable from terminal clients and later notebook
or frontend clients. A browser will require a Node server interface; it cannot
import the SQLite backend directly. A Python notebook will need a bridge to Node.

## Reference and explicit decisions

Reference: Ventura's PR #139 in `venturars/neoland-102026`, reviewed at commit
`e50b7cd850c2a98ea0c477f6e7348ddbfa353531`:
https://github.com/venturars/neoland-102026/pull/139

Its AGENTS guide, constitution, email-lookup operation, and terminal example are
teaching material. They are not active instructions for this separate project.

The reference contains transitional inconsistencies:

- Its current CRUD operations return ordinary data and throw ordinary errors.
  This project follows that contract too.
- Its constitution describes separate SQL files, but its query module still
  contains inline SQL. Here SQL text will live in `queries/sql/` from the start.
- Its email-lookup example calls `.trim()` before checking the input type. Here
  type validation must happen before string operations.

The following choices were explicit assumptions, approved with this foundation
on 2026-10-19. They were not inherited requirements from the earlier `first-app`.
Changing them requires a reviewed amendment:

- Keep the reference's 64-character email limit for easy classroom comparison.
- Require a dot in the email domain and reject whitespace/null characters to
  catch obvious input mistakes the reference's single-`@` check misses.
- Limit names to 100 Unicode code points to keep input bounded. Count code points,
  not bytes; a combined visible character may contain multiple code points.
- Use UTC timestamps rather than local time so records have one interpretation
  across computers. Timestamp values have second precision.
- Reject unknown fields and empty update patches to expose caller mistakes.
- IDs are positive JavaScript safe integers generated by SQLite.

Use these contracts for new code in this folder. Do not copy a conflicting
reference convention or silently amend a contract to match an implementation.
A feature specification may add detail but cannot override this constitution
without an explicit reviewed amendment.

## Planned structure and responsibilities

The following is the intended full structure. Specification 001 authorizes only
runtime setup, connection, initialization queries/client, and acceptance tests.
Specification 002 additionally authorizes user creation and its queries/client/tests.
Specification 003 additionally authorizes updating and its queries/client/tests.
Specification 004 additionally authorizes deletion and its query/client/tests.
Specification 005 additionally authorizes listing and its query/client/tests.
Specification 006 additionally authorizes public email lookup and its client/tests.
No integration features are authorized by these specifications.

```text
first-app-ssd/
  AGENTS.md
  package.json                 Node/module setup and commands, defined later
  db/
    connection.js              Opens and exports the single connection
    users.sqlite               Generated local data; never committed
  queries/
    sql/                       One SQL statement string per file
    users.js                   Prepares and executes SQL; no business rules
  logic/
    create-user.js
    update-user.js
    delete-user.js
    list-users.js
    find-user-by-email.js
  clients/
    terminal/                  Copyable manual initialization/operation examples
  docs/
    CONSTITUTIONS.md
    specs/                     Reviewed feature specifications and small plans
```

The initialization client calls the query module to create the table.
CRUD clients call `logic/`, which calls `queries/users.js`, which uses `db`.
No client duplicates business validation. No business function contains SQL.
Query functions return a row, an array of rows, or an affected-row count as
needed; a single-row lookup with no match returns `undefined`. They do not
throw business errors for a missing user. Business functions interpret those
results and construct the public response. Exact internal query signatures
belong to the feature specification that introduces them.

## Database and connection lifecycle

Use Node's built-in `node:sqlite` with a supported Node version selected and
verified in the initialization specification. Use one database at
`db/users.sqlite`, resolved relative to `connection.js`, not the terminal's
working directory. There is one connection per Node process: importing
`db/connection.js` exports that connection; other modules reuse it. Opening it
creates the database file if necessary but does not create application tables.

The top-level client owns connection lifetime and closes `db` in `finally`.
Business functions and query functions do not open or close it. A notebook may
keep that one connection for its session, closing it at the end. Once closed,
that module's connection is not automatically reopened; start a new process or
restart the notebook kernel for a new session. No pool or connection factory.

Initialize explicitly before calling business operations. Initialization creates
the `users` table if missing; repeating it preserves records and succeeds. It
does not seed users, reset data, or silently migrate incompatible schemas. A
future schema change requires its own reviewed migration specification. If an
existing `users` table does not match the agreed schema, initialization must
report failure and preserve its records instead of claiming success. Exact
schema checks and the initialization failure message belong to its feature spec.

Table contract:

| Field | Storage and behavior |
| --- | --- |
| `id` | `INTEGER PRIMARY KEY`, generated by SQLite, immutable |
| `name` | Required `TEXT`; stored trimmed; 1–100 code points |
| `email` | Required `TEXT`; stored trimmed/lowercased; unique; at most 64 code points |
| `createdAt` | Required `TEXT`, UTC `YYYY-MM-DD HH:MM:SS`, assigned on insertion |
| `updatedAt` | Required `TEXT`, same format, assigned on insertion and refreshed on successful update |

`createdAt` never changes. Two updates within one second may have equal
`updatedAt` values. Do not use timestamps as unique identifiers or version locks.
`INTEGER PRIMARY KEY` can reuse a deleted ID; never promise globally increasing
IDs or add `AUTOINCREMENT` without a concrete need.

Enforce required fields, supported length bounds, and email uniqueness in SQLite
as a final safeguard. The business layer validates format and normalizes values.
Use SQLite `NOCASE` uniqueness as an additional ASCII case safeguard; full
Unicode case folding is not promised. All public writes normalize emails first.
SQL uses named bound parameters (`:id`, `:name`, `:email`). No user-built SQL.

## Common business contract

Each operation validates inputs, checks business rules, performs the operation,
and returns explicitly selected ordinary JavaScript data, in that order. Query
results must not be returned directly as SQLite-specific row objects.

The initial business and query functions are synchronous: they return a value
immediately or throw, rather than returning a Promise. This matches the simple
synchronous SQLite API; async interfaces can be proposed separately if needed.

A returned user has exactly these fields:
`{ id, name, email, createdAt, updatedAt }`.
No SQL metadata, passwords, or internal error details leave `logic/`.

Validate types before string operations. Normalize email by trimming and
lowercasing **before** checking its final length and format. An email must have
exactly one `@`, a nonempty local part, at least two nonempty dot-separated
domain labels, no whitespace, and no null characters. For example, `a@b.c`
is accepted; `a@b`, `a@.b`, `a@b.`, `a@b..c`, and `a b@c.d` are rejected. This is a
basic shape check, not a complete email standard parser or mailbox verification.
Do not remove internal whitespace to make an invalid address valid.

Names must be strings, trimmed, nonempty, no null characters, and at most 100
code points. There is no lowercasing of names. ID inputs must be numbers that
are positive safe integers; string-to-number conversion belongs to a client.
Inputs such as `null`, booleans, or arrays must fail predictably, not cause
uncontrolled JavaScript type errors.

Amendment approved by Miguel's cross-review fix request on 2026-10-19: name and
email inputs must be well-formed Unicode strings, with no unmatched UTF-16
surrogates. Reject malformed names with `Name is invalid` and malformed emails
with `Email is invalid`, before normalization/storage. Do not silently replace
characters; valid surrogate pairs such as emoji remain supported.

All query result columns must have explicit canonical aliases (`id`, `name`,
`email`, `createdAt`, `updatedAt`) so accepted schema capitalization differences
do not change result object keys. Acceptance tests must check both stdout and
stderr for unintended library output, allowing Node's normal SQLite warning.


## Public operation signatures

| Function | Success | Rules |
| --- | --- | --- |
| `createUser(name, email)` | New plain user object | Validate both fields; reject duplicate normalized email |
| `updateUser(id, changes)` | Updated plain user object | Validate ID and patch; require existing user; preserve omitted fields |
| `deleteUser(id)` | `undefined` | Validate ID; require existing user; permanently delete it |
| `listUsers()` | Array of plain user objects | Ascending numeric ID; empty table returns `[]` |
| `findUserByEmail(email)` | One plain user object | Validate/normalize email; missing match is an error |

`changes` is a plain object containing one or both own fields `name` and `email`.
The patch object is intentional: it distinguishes omitted update fields and
avoids positional placeholder arguments. Creation uses positional fields as our approved choice; Ventura's actual
createUser function accepts an object containing name and email. A plain object here means an object
with `Object.prototype` or `null` as its prototype; arrays and class instances
are invalid. Its own property names must be only `name` and/or `email`; inherited
values do not count as supplied fields. Unknown fields, an empty patch,
and supplied `null` or `undefined` values are invalid. IDs/timestamps cannot be
changed. Reusing your own normalized email is allowed; taking another user's
email is not. A successful update with the same values is allowed and refreshes
`updatedAt` (subject to second precision).

Error precedence is deterministic: create validates name then email; update
validates ID, patch shape, supplied name, then supplied email before checking user
existence and duplicate ownership. Delete validates ID before checking existence.
Email lookup validates email before querying. No failed validation writes data.
Query preparation/execution happens inside query function calls, not at module
import time, so an uninitialized table does not prevent input validation or
explicit table initialization. The connection itself still opens on import as
defined above.
An update/delete that discovers a missing row at write time also reports
`User not found` rather than returning success with missing data.

## Errors

Use ordinary `throw new Error(message)`. No custom error classes, result wrappers,
or error-code properties. Clients catch errors; only clients print or set exit
status. Unexpected database exceptions are replaced with the operation's generic
message. Catch only database operations so validation/business errors are not
accidentally masked.

| Condition | Exact message |
| --- | --- |
| Blank name after trimming | `Name is empty` |
| Non-string name, length overflow, or null characters | `Name is invalid` |
| Invalid email | `Email is invalid` |
| Invalid ID | `Id is invalid` |
| Invalid patch shape, unknown/forbidden fields, empty patch | `Changes are invalid` |
| Another user owns the normalized email | `Email is already used` |
| No matching user for update/delete/email lookup | `User not found` |
| Database failure during create | `Could not create the user` |
| Database failure during update | `Could not update the user` |
| Database failure during delete | `Could not delete the user` |
| Database failure during list | `Could not list the users` |
| Database failure during email lookup | `Could not find the user` |

A supplied update field with an invalid value uses its field's error message.
Business functions perform no console output and do not attach the original
database error as a public `cause`. Database-opening failures happen before
business execution and are handled by the client; their exact presentation is
defined by the initialization/client specification.
The initialization specification must define initialization errors separately.
A duplicate-email check is not sufficient under concurrent writers: retain the
SQLite unique constraint, and translate a write-time email unique-constraint
failure to `Email is already used`; other database failures use generic messages.
Do not leak SQLite error text. Supporting concurrent edits or resolving lost
updates is outside this local single-user exercise.

## Specification and acceptance requirements

Every feature specification states its goal, inputs, outputs, exact errors,
examples, exclusions, prerequisites, and numbered acceptance checks with
concrete expected results. Its implementation plan follows review. Approval
must precede implementation; this constitution is not approval of every feature.

Acceptance checks must cover successful behavior, relevant validation boundaries,
expected failures, and unchanged records after rejected writes. Use disposable
project copies and SQLite files for automated checks, never the learner's working
database. Each feature includes a terminal client with clear prerequisites and
working-directory instructions. Initialization remains a separate action.
