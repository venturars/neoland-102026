# Lo último del flujo de git en first-app y asistenciapp

Issue: #1163.

Quien pide un cambio en first-app o en asistenciapp usa el flujo de git de cada app. Ese flujo ya está y cada app tiene ajustes pequeños propios. Falta recoger solo lo último del curso, el mismo en las dos apps, sin sustituir lo que ya se adaptó.

Al empezar un cambio, la petición nace en borrador y queda asignada a quien la abre, en un solo paso.

Al pedir revisión, se dicen nombres de compañeros. Se reutilizan los que ya se resolvieron. No se inventa un login. Si un nombre no está claro, se pregunta.

Hay un tipo de tarea para dejar escrito lo aprendido, con su plantilla de issue y de petición.

Al guardar un trozo, el mensaje admite ese tipo y puede llevar el detalle de ese commit.

Al pensar una tarea, se hacen las preguntas que hagan falta de una vez, cada una con una respuesta recomendada, y se espera. Si el problema, el resultado, el alcance y cómo comprobarlo ya están claros, se puede dejar escrita sin otra entrevista.

Lo que ya decía cada app se queda: un pedido que cambia el proyecto entra por el flujo; si la tarea ya está en curso, sigue en su fase; se piensa la tarea solo si es nueva; una pregunta no abre el flujo; hay paradas en spec, plan y tareas; la spec no espera a pedir revisión.

Ejemplo: se pide revisión para Dietor y Victor. Si esos nombres ya se resolvieron, se piden esas revisiones y la petición sale de borrador. Si uno no está claro, se pregunta y no se asigna un login inventado.

Si el flujo de una app ya tiene un texto propio, ese texto no se borra para copiar el curso entero. Si algo no es de lo último, no entra.

Queda fuera sustituir el flujo entero, listar usuarios, pasar lista, el cliente HTTP de Node, un paquete nuevo y un mensaje nuevo de la aplicación. La lógica, la base, las pantallas y el paso de lista se quedan como están.
