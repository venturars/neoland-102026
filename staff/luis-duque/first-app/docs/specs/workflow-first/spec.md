# El pedido entra por el flujo

Un pedido que cambie algo en esta app entra primero por el flujo de git: pensar una tarea, dejarla escrita, empezar, guardar un trozo o pedir revisión. Si el pedido ya nombra el momento, se usa ese. Si no nombra ninguno, se piensa la tarea.

Una pregunta sobre el proyecto se responde. Un mensaje que no provoque un cambio en el proyecto también. Ninguno de los dos abre el flujo.

Pedir el cambio no abre el código y no escribe la spec como primera respuesta. Después del flujo, un desarrollo nuevo sigue parando en la spec, en el plan y en las tareas. Ese flujo no se salta esas paradas.

Lo mismo vale en asistenciapp. Un cambio entra primero por su flujo de git. Una pregunta, o un mensaje que no cambie esa app, no lo abre. Las paradas de especificar, planificar, desglosar e implementar siguen.

La aplicación sigue haciendo lo mismo con los usuarios. Pasar lista sigue igual. No se añade ningún paquete. Pasar el trabajo a staging queda fuera.
